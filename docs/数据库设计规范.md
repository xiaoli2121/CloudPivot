# CloudPivot 数据库设计规范

## 1. 目标与原则

CloudPivot 数据库规范以 MySQL 为主设计，同时保证 PostgreSQL 兼容性。核心原则如下：

- 优先兼容：避免深度依赖单一数据库方言
- 优先规范：统一命名、主键、索引、审计字段和逻辑删除策略
- 优先可维护：表结构清晰，字段含义明确，避免隐式约定
- 优先扩展：兼顾低代码元数据模型的灵活性

## 2. 数据库适配策略

### 2.1 主数据库

- 社区版默认使用 MySQL

### 2.2 兼容数据库

- 必须兼容 PostgreSQL

### 2.3 兼容约束

- 避免使用仅 MySQL 支持的隐式行为
- 避免使用强依赖自增策略的跨库不一致写法
- 避免直接使用保留关键字作为表名和字段名
- 尽量使用标准 SQL 语法与应用层统一分页封装

## 3. 命名规范

### 3.1 表命名

- 使用小写英文与下划线
- 表名采用业务域前缀 + 实体名方式
- 中间表使用 `_rel` 或 `_map` 后缀

示例：

- `iam_user`
- `iam_role`
- `iam_user_role_rel`
- `meta_object`

### 3.2 字段命名

- 使用小写英文与下划线
- 布尔或状态类字段尽量体现语义，例如 `enabled_flag`
- 时间字段统一使用 `*_time`

示例：

- `user_name`
- `role_code`
- `created_time`
- `updated_time`

## 4. 主键规范

- 统一采用 `bigint` 作为主键类型
- 主键字段统一命名为 `id`
- 主键值由应用层统一生成，避免强绑定数据库自增策略

推荐原因：

- 兼容 MySQL 与 PostgreSQL
- 适合平台型项目跨模块统一主键管理

## 5. 通用审计字段

业务主表建议统一包含以下字段：

- `id`
- `created_by`
- `created_time`
- `updated_by`
- `updated_time`
- `deleted_flag`
- `version_no`

说明：

- `deleted_flag`：逻辑删除标识，`0` 表示未删除，`1` 表示已删除
- `version_no`：乐观锁版本号，默认从 `0` 开始

## 6. 字段类型建议

### 6.1 字符类

- 短文本：`varchar`
- 长文本：`text`
- 编码类字段：`varchar(64)` 或 `varchar(128)`

### 6.2 数值类

- 主键与关联 ID：`bigint`
- 状态值：`smallint` 或 `integer`
- 金额：`numeric(18,2)`

### 6.3 时间类

- 统一使用 `timestamp` 或应用层统一映射的时间类型
- 避免在 SQL 中过度依赖数据库时间函数差异

### 6.4 JSON 类

- 核心结构化元数据优先建模为关系表
- 灵活配置项可使用 `text` 存储 JSON 字符串
- 若后续启用 JSON 字段能力，需要保证 MySQL 与 PostgreSQL 双端测试通过

## 7. 索引规范

- 每张表必须明确主键
- 唯一业务编码必须建立唯一索引
- 高频查询字段建立普通索引
- 多字段组合查询使用联合索引
- 避免无实际价值的冗余索引

建议索引场景：

- `role_code`
- `user_name`
- `org_id`
- `deleted_flag + status`

## 8. 逻辑删除规范

- 优先采用逻辑删除，不建议直接物理删除核心业务数据
- 逻辑删除字段统一使用 `deleted_flag`
- 查询语句必须默认过滤已删除数据

例外：

- 日志归档表
- 临时缓存表
- 明确可清理的中间数据

## 9. 外键与约束规范

- 社区版 1.0 优先由应用层维护业务一致性
- 可保留基础非空、唯一约束
- 跨模块关系建议弱化数据库级外键，避免复杂升级与迁移问题

原因：

- 平台型项目后续模块独立演进频繁
- 低代码模型和插件扩展需要更高灵活性

## 10. SQL 编写规范

- 显式列出字段，禁止 `select *`
- 禁止在 SQL 中依赖数据库默认排序行为
- 避免使用难以跨库兼容的函数
- 分页、排序通过统一访问层封装
- 复杂 SQL 必须写清楚注释和用途

## 11. 元数据表设计原则

低代码元数据相关表设计应遵循：

- 对象、字段、页面、组件、发布版本分表管理
- 设计态数据与运行态发布数据适度隔离
- 支持草稿、已发布、历史版本三类状态
- 可变配置放在扩展字段中，但核心主干必须结构化建模

## 12. 多数据库兼容注意事项

需要重点规避的问题：

- MySQL 与 PostgreSQL 在大小写、时间函数、分页语法、布尔值表达上的差异
- 自增主键策略差异
- JSON 和全文索引能力差异

建议方式：

- 通过 ORM 与统一 SQL 规范控制差异
- 对复杂数据库差异点提供独立适配层
- 核心 DDL、DML 在双数据库环境下进行验证

## 13. 规范结论

CloudPivot 数据库规范以统一、兼容、可维护为主线。坚持 MySQL 主库与 PostgreSQL 兼容策略，能够在保证社区版快速落地的同时，为后续多场景部署和企业级演进提供稳固的数据底座。
