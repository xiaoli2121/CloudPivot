# CloudPivot 后端架构设计

## 1. 设计目标

CloudPivot 后端架构在社区版阶段采用模块化单体模式，目标是：

- 保证系统快速启动、易于部署和便于调试
- 保持业务模块边界清晰，利于后续演进
- 支撑认证授权、系统管理、低代码元数据和插件扩展
- 为未来服务拆分保留清晰的模块拆分路径

## 2. 工程组织

根工程为 `cloudpivot-springboot`，采用 Maven 聚合工程形式组织。

### 2.1 启动模块

- `cloudpivot-boot`：应用统一启动、配置加载、模块装配

### 2.2 基础模块

- `cloudpivot-common`：通用对象、异常、上下文、工具、基础配置

### 2.3 业务模块

- `cloudpivot-auth`
- `cloudpivot-iam`
- `cloudpivot-system`
- `cloudpivot-metadata`
- `cloudpivot-generator`
- `cloudpivot-designer`
- `cloudpivot-workflow`
- `cloudpivot-rule`
- `cloudpivot-integration`
- `cloudpivot-plugin`
- `cloudpivot-tenant`

## 3. 架构风格

后端采用“模块化单体 + 分层设计”的方式。

每个模块内部建议分为：

- `interfaces`：Controller、DTO、请求响应对象
- `application`：应用服务、用例编排
- `domain`：领域对象、领域服务、业务规则
- `infrastructure`：Mapper、持久化实现、外部适配

社区版早期可以先不强制严格目录分层，但必须坚持职责分离，避免 Controller 直接写业务与 SQL。

## 4. 模块通信原则

- 模块之间通过服务接口或应用服务协作
- 公共能力沉淀到 `cloudpivot-common`
- 禁止跨模块直接访问彼此持久化层
- 禁止形成循环依赖

推荐方式：

- 读操作通过接口服务提供查询能力
- 写操作通过应用服务进行编排
- 共享对象使用明确的 DTO 或查询对象传递

## 5. API 设计规范

### 5.1 接口风格

- 使用 RESTful 风格为主
- 统一以 `/api` 为根路径
- 统一响应结构
- 统一异常码和错误消息

### 5.2 响应结构建议

- `code`：业务状态码
- `message`：提示信息
- `data`：业务数据
- `traceId`：链路追踪标识，可选

### 5.3 分页与查询

- 分页查询统一请求对象
- 排序字段白名单控制
- 数据权限条件由服务层统一注入

## 6. 安全架构

- 使用 Shiro 完成认证与授权
- 通过自定义过滤器处理 Token
- 通过 Realm 加载用户和权限信息
- 在服务层统一进行权限与数据范围校验

## 7. 数据访问架构

- 采用 MyBatis-Plus 进行基础 CRUD 与分页封装
- 复杂查询通过 XML 编写显式 SQL
- 数据库规范以 MySQL 为主，兼容 PostgreSQL
- 持久化层与业务层分离，避免 SQL 泄漏到控制层

## 8. 配置与环境管理

- 使用 YAML 进行环境配置
- 启动模块集中管理公共配置
- 各业务模块只定义本模块所需配置项
- 后续可扩展 Nacos 或其他配置中心，但社区版 1.0 不作为刚性依赖

## 9. 日志、异常与审计

### 9.1 日志

- 按应用日志、访问日志、审计日志分类
- 错误日志必须包含上下文信息与追踪标识

### 9.2 异常

- 建立统一业务异常体系
- 控制器层统一异常处理，返回标准错误结构

### 9.3 审计

- 登录、退出、角色授权、菜单变更、配置变更等关键操作记录审计日志

## 10. 低代码后端支撑

后端需要为低代码能力提供以下核心支撑：

- 元数据定义存储
- 元数据校验与版本管理
- 页面发布与运行态读取
- 动态查询与基础数据映射
- 插件与设计器扩展点的服务支撑

## 11. 插件化支撑

后端插件体系至少支持：

- 插件注册信息管理
- 扩展点声明
- 启停状态管理
- 插件配置项管理

后端模块应对插件保持开放，但不能让插件绕过核心安全与权限边界。

## 12. 社区版 1.0 落地重点

- 完成统一启动模块与基础模块
- 完成认证、IAM、系统基础模块的主链路
- 完成元数据和设计器基础服务骨架
- 完成统一接口规范、异常处理和日志治理基础设施

## 13. 演进路线

后续随着模块成熟度提升，后端可逐步向以下方向演进：

- 读写分离与缓存增强
- 模块拆分为独立服务
- 消息驱动与异步任务增强
- 多租户隔离加强
- 流程和规则中心增强

## 14. 设计结论

CloudPivot 后端以模块化单体作为社区版最优解，既能保障快速落地和统一治理，又能通过清晰边界为未来分布式演进预留空间，适合快速开发平台的初期建设阶段。
