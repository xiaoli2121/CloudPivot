# CloudPivot 总体架构

## 1. 架构目标

CloudPivot 总体架构围绕“快速交付、低代码驱动、企业级扩展”三个目标设计：

- 以前后端分离保证交互体验与团队协作效率
- 以后端模块化单体保证启动快、部署简单、边界清晰
- 以元数据和插件化机制支撑低代码与行业扩展能力

## 2. 总体分层

平台整体分为五层：

### 2.1 访问层

- PC 管理端：管理后台、设计器、运行容器
- 移动端：uni-app 工程承载移动端和小程序访问入口
- 第三方接入端：开放 API、Webhook、集成接口

### 2.2 应用层

- Admin Shell：统一后台入口，承载菜单、权限、工作台与系统管理
- Designer Studio：低代码设计态，承载模型、页面、表单和发布能力
- Runtime App：运行态容器，基于元数据渲染业务页面
- Portal App：门户与外部业务入口预留

### 2.3 平台服务层

- 认证与权限服务
- 组织与身份管理服务
- 系统基础服务
- 元数据与设计器服务
- 代码生成服务
- 规则、流程、插件、集成等扩展服务

### 2.4 数据与基础设施层

- 主数据库：MySQL
- 兼容数据库：PostgreSQL
- 缓存与会话：Redis
- 文件存储：本地或对象存储适配
- 日志与监控：日志框架、健康检查、指标扩展

### 2.5 扩展层

- 前端插件扩展点
- 后端插件扩展点
- 行业模板和元数据模板
- 第三方系统连接器

## 3. 工程形态

### 3.1 前端工程

`cloudpivot-vue3` 采用多应用工作区结构：

- `apps/admin-shell`：平台管理后台
- `apps/designer-studio`：低代码设计器
- `apps/runtime-app`：低代码运行容器
- `apps/portal-app`：门户预留
- `packages/*`：公共 UI、SDK、运行时、设计器核心等共享包

### 3.2 后端工程

`cloudpivot-springboot` 采用模块化单体结构：

- `cloudpivot-boot`：统一启动装配模块
- 领域能力模块：`auth`、`iam`、`system`、`metadata`、`designer` 等
- 公共基础模块：`cloudpivot-common`

在社区版阶段，各模块以统一进程部署，强调清晰边界和可拆分性；后续可根据模块成熟度逐步拆分服务。

## 4. 核心业务链路

### 4.1 认证授权链路

用户通过前端登录页提交凭证，后端认证服务基于 Shiro 完成身份校验并签发访问令牌。前端携带令牌访问各模块 API，网关职责由前端统一请求层和后端认证过滤器共同承担。后端根据角色、资源、数据权限完成授权判断。

### 4.2 低代码设计链路

设计人员在 Designer Studio 中配置对象、页面、字段、布局和交互规则。前端将设计结果提交至元数据服务，后端完成校验、存储、版本管理与发布。发布后的元数据由 Runtime App 加载并渲染为运行页面。

### 4.3 平台管理链路

管理员在 Admin Shell 中管理组织、用户、角色、菜单、字典、参数和系统配置。后端各业务模块提供统一 REST API，前端通过共享 SDK 进行调用。

## 5. 部署形态

### 5.1 开发环境

- 前端应用通过 Vite 启动
- 后端通过 Spring Boot 打包运行
- 前端通过代理访问后端 API

### 5.2 测试与生产环境

- 前端静态资源部署到 Nginx
- 后端以单体可执行包部署
- Redis 负责缓存、令牌状态与高频数据
- MySQL 为主数据库，PostgreSQL 作为兼容部署选项

## 6. 架构原则

- 统一标准：统一认证、统一接口风格、统一错误码、统一日志规范
- 模块清晰：每个模块单一职责，禁止跨模块绕过边界直接耦合
- 元数据优先：能通过配置驱动的能力，优先不要写死在业务代码中
- 插件扩展：面向行业扩展和二次开发预留可插拔机制
- 先稳后广：社区版先保证基本链路可运行，再逐步扩展高级能力

## 7. 社区版 1.0 的总体交付范围

社区版 1.0 在总体架构上重点落地以下闭环：

- 后端可运行的模块化单体底座
- 前端可运行的管理台入口
- 基础认证授权与组织权限模型
- 元数据中心和设计器基础骨架
- 插件扩展机制基础设施

这套总体架构既能支撑当前 MVP，也能为后续流程、规则、租户和行业能力扩展打下统一基础。
