# CloudPivot 核心模块设计

## 1. 模块设计目标

核心模块设计的目标是让 CloudPivot 在社区版 1.0 阶段具备清晰的业务边界、稳定的基础能力和可扩展的低代码支撑能力。模块设计遵循“高内聚、低耦合、边界清晰、统一标准”的原则。

## 2. 核心模块清单

### 2.1 启动装配模块 `cloudpivot-boot`

职责：

- 作为后端统一启动入口
- 装配所有业务模块与基础组件
- 提供健康检查、基础配置和统一运行环境

边界：

- 不承载具体业务逻辑
- 只负责启动、配置装配和模块集成

### 2.2 公共基础模块 `cloudpivot-common`

职责：

- 提供通用常量、基础枚举、异常体系、响应对象和工具类
- 提供统一日志、审计、分页、上下文和基础扩展能力
- 为各业务模块提供共享技术底座

边界：

- 不包含具体业务概念
- 不直接依赖上层业务模块

### 2.3 认证模块 `cloudpivot-auth`

职责：

- 登录、退出、令牌刷新、会话失效处理
- 基于 Shiro 的认证拦截、身份上下文和安全校验
- 登录策略、密码策略和账号状态校验

边界：

- 只负责身份认证与令牌管理
- 权限模型、组织模型由 IAM 模块负责

### 2.4 身份与权限模块 `cloudpivot-iam`

职责：

- 组织、部门、岗位、用户、角色管理
- 菜单、按钮、接口资源权限管理
- 数据权限规则定义与授权关系维护

边界：

- 不负责登录认证实现
- 不负责低代码业务模型定义

### 2.5 系统基础模块 `cloudpivot-system`

职责：

- 字典、参数、消息、附件、日志、任务等通用系统能力
- 系统配置、基础资源管理和后台治理能力
- 为所有业务模块提供通用平台功能

边界：

- 不承载特定行业业务
- 不与低代码设计元数据强耦合

### 2.6 元数据中心模块 `cloudpivot-metadata`

职责：

- 业务对象、字段、页面、表单、视图等元数据存储与版本管理
- 元数据校验、发布和运行态读取能力
- 为设计器与运行容器提供统一模型来源

边界：

- 不直接负责前端可视化设计交互
- 不直接承担页面运行渲染逻辑

### 2.7 设计器服务模块 `cloudpivot-designer`

职责：

- 承载低代码设计态服务能力
- 提供设计稿保存、组件配置、发布编排与草稿管理
- 对接元数据模块完成设计结果持久化

边界：

- 不负责运行态数据查询与页面渲染
- 设计结果最终落地到元数据中心

### 2.8 代码生成模块 `cloudpivot-generator`

职责：

- 根据元数据或模板生成前后端基础代码
- 支持表结构驱动、模板驱动和模块驱动生成
- 作为低代码与代码开发结合的桥梁

边界：

- 不替代运行时渲染引擎
- 不直接负责生产运行逻辑

### 2.9 流程模块 `cloudpivot-workflow`

职责：

- 预留流程定义、任务流转和审批能力的后端接口基础
- 为后续增强版流程能力提供演进入口

边界：

- 社区版 1.0 以模块骨架和接口预留为主

### 2.10 规则模块 `cloudpivot-rule`

职责：

- 预留表单规则、业务校验和动作编排能力
- 支撑未来复杂业务规则中心建设

边界：

- 社区版 1.0 不追求完整规则引擎实现

### 2.11 集成模块 `cloudpivot-integration`

职责：

- 预留第三方系统接入、Webhook、消息回调和连接器机制
- 提供标准接口适配与接入点管理

### 2.12 插件模块 `cloudpivot-plugin`

职责：

- 管理插件注册、启停、能力声明和扩展点绑定
- 为前后端插件机制提供后端侧支撑

### 2.13 租户模块 `cloudpivot-tenant`

职责：

- 预留多租户配置、隔离和运营能力
- 为后续增强版租户体系打基础

边界：

- 社区版 1.0 以能力预留为主，不强推复杂租户运营逻辑

## 3. 前端核心应用模块

### 3.1 管理后台 `admin-shell`

- 登录、首页、工作台、系统管理入口
- 用户、角色、菜单、组织、参数等平台管理能力

### 3.2 设计器工作台 `designer-studio`

- 页面设计、表单设计、对象配置和发布入口

### 3.3 运行容器 `runtime-app`

- 基于元数据渲染页面、表单和列表
- 处理运行态数据交互与页面生命周期

### 3.4 门户入口 `portal-app`

- 面向业务门户和对外应用预留的应用入口

## 4. 模块依赖关系

后端依赖关系遵循以下规则：

- `cloudpivot-boot` 依赖所有启用业务模块
- 业务模块统一依赖 `cloudpivot-common`
- `cloudpivot-auth` 可以依赖 `cloudpivot-iam` 读取身份与权限信息
- `cloudpivot-designer` 与 `cloudpivot-generator` 依赖 `cloudpivot-metadata`
- `cloudpivot-plugin` 提供跨模块扩展能力，但不直接侵入业务核心

禁止出现：

- 业务模块之间循环依赖
- 下层基础模块依赖上层业务模块
- 为图方便在模块间直接复制业务逻辑

## 5. 社区版 1.0 核心落地优先级

优先级 P0：

- 启动装配模块
- 公共基础模块
- 认证模块
- IAM 模块
- 系统基础模块
- 元数据中心模块
- 管理后台

优先级 P1：

- 设计器服务模块
- 运行容器
- 插件模块
- 代码生成基础能力

优先级 P2：

- 流程、规则、集成、租户的骨架与扩展预留

## 6. 模块设计结论

CloudPivot 的核心模块设计不是一次性追求大而全，而是在社区版 1.0 先构建完整平台骨架，优先打通“登录授权 + 平台管理 + 元数据驱动 + 基础低代码 + 扩展预留”主链路，为后续行业项目落地提供稳定底座。
