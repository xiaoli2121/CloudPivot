# CloudPivot 插件体系设计

## 1. 设计目标

插件体系是 CloudPivot 面向行业扩展和二次开发的重要能力，目标如下：

- 允许在不破坏核心平台的前提下扩展功能
- 支持前后端双侧扩展
- 支持低代码物料、页面能力和业务模块扩展
- 支持后续建立行业模板与插件市场

## 2. 插件体系定位

CloudPivot 插件体系不是简单的“工具脚本集合”，而是平台标准扩展机制，主要承载以下能力：

- 行业模块扩展
- 组件物料扩展
- 页面与菜单扩展
- 数据源和连接器扩展
- 工作台与门户扩展

## 3. 插件分类

### 3.1 前端插件

前端插件可扩展：

- 菜单与路由
- 页面组件
- 设计器物料
- 工作台卡片
- 运行时动作

### 3.2 后端插件

后端插件可扩展：

- 业务服务能力
- 接口资源
- 数据源适配
- 集成连接器
- 插件配置项

### 3.3 模板类插件

模板类插件主要包括：

- 行业模板
- 页面模板
- 表单模板
- 低代码对象模板

## 4. 核心设计要素

### 4.1 插件清单

每个插件应至少包含：

- 插件编码
- 插件名称
- 版本号
- 插件类型
- 依赖声明
- 扩展点声明
- 配置项声明
- 启用状态

### 4.2 扩展点

扩展点是平台暴露给插件的标准挂载位置，例如：

- 菜单扩展点
- 路由扩展点
- 设计器组件扩展点
- 运行时动作扩展点
- 后端服务扩展点

### 4.3 生命周期

插件生命周期建议包括：

- 注册
- 安装
- 启用
- 停用
- 卸载

## 5. 前端插件机制

前端插件采用注册式装配模式：

- 插件声明可扩展的菜单、路由、组件和物料
- 系统启动时扫描插件配置并注册
- 根据启用状态控制插件可见性

前端需要注意：

- 插件不能破坏主应用路由与权限边界
- 插件 UI 需要遵循统一设计规范
- 插件元数据需支持版本控制

## 6. 后端插件机制

后端插件机制建议采用“注册表 + 扩展接口”模式：

- 插件注册到插件中心
- 插件声明所实现的扩展接口和能力清单
- 平台在启动或加载时将插件挂接到对应扩展点

社区版阶段优先支持轻量插件接入，不追求过度复杂的热插拔。

## 7. 安全与隔离

插件必须遵循以下约束：

- 所有接口必须经过平台统一认证授权
- 插件不能绕过主平台权限校验
- 插件配置必须可审计
- 插件异常不能影响核心平台主链路稳定性

## 8. 版本与兼容性

插件体系需要管理以下兼容关系：

- 插件版本与平台版本兼容性
- 插件依赖插件之间的版本约束
- 插件升级后的元数据兼容性

建议：

- 统一版本规范
- 插件清单记录最低平台版本要求
- 重大升级时提供兼容提示

## 9. 插件场景示例

### 9.1 行业业务插件

通过插件方式加入某行业的业务模块、菜单、页面模板和数据字典。

### 9.2 设计器物料插件

新增行业专属组件，例如证照信息组件、地理位置组件、审批轨迹组件。

### 9.3 集成插件

扩展第三方消息、对象存储、电子签章等连接器能力。

## 10. 社区版 1.0 落地范围

优先落地：

- 插件清单模型
- 前端菜单与路由扩展点
- 设计器物料扩展点
- 后端插件注册表基础能力

暂缓复杂能力：

- 插件市场
- 在线安装中心
- 完整热插拔机制

## 11. 设计结论

CloudPivot 插件体系的核心价值在于“稳定内核 + 标准扩展”。社区版阶段先打好扩展点、清单模型和装配机制基础，为未来行业能力沉淀、模板市场和商业化支持建立长期基础。
